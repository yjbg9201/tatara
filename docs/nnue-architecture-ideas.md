## 1. 共通規約（全アイデアに適用）

### 1.1 三重実装のズレを防ぐ

新しい特徴を1つ足すと、以下の3系統を整合させる必要がある。ここがズレると「学習は回るのに推論で弱い」不具合になり、検出が難しい。

1. エンジン推論側（YaneuraOu `source/eval/nnue/features/*.h`：`kDimensions` / `kMaxActiveDimensions` / `AppendActiveIndices` / `AppendChangedIndices` / `kRefreshTriggers`）
2. 学習データローダ側（PackedSfenをデコードして同じindexを生成するコード）
3. モデル・シリアライズ側（次元・factorizer・量子化・`.nnue`書き出し）

規約:
- `MakeIndex` / バケット関数 / スカラー特徴計算は**単一の定義**に置き、推論とローダの両方から使う（C++なら共有ヘッダ。Rust学習器なら同じ式をテストで突合）。
- 量子化定数（`FV_SCALE=16`、FT weight scale=127、hidden scale=64）を1か所に集約する。
- **ハッシュ値は必ず新規採番**し、既存 `.nnue` の誤ロードをロード時に弾く。

### 1.2 検証プロトコル（この順で実施）

1. **index整合**: ランダム1万局面で「推論側indexリスト == ローダ側indexリスト」を突合
2. **integer-exact**: 量子化済み学習器forwardとエンジン `Evaluate()` の完全一致（±0）
3. **差分更新整合**: 同一局面を「全計算」と「1手ずつ差分更新」で比較（ランダムプレイアウト）
4. **棋力測定**: 下記 §1.3 の条件で

### 1.3 棋力比較の条件

- **固定ノード数**対局で評価精度の差（Eloの上限）を見る
- **固定時間**対局でNPS低下込みの実効値を見る
- 後段の変更は持ち時間で結論が変わりやすいため、**短・長の2種類**で測る
- メモリ量を揃えた比較も必要に応じて（C2）
- 入玉関連（A2〜A4）は通常局面のレート変化（目安±20以内）と、入玉局面集での宣言勝ち到達率を別々に測る

### 1.4 初期化（パラメータ移植）

既存ツール `nnue_surgery.py`（numpy、サブコマンド `ft-transplant` / `widen` / `deepen` / `stacks` / `verify` / `inspect` / `convert`）を使う。手術は**量子化前のfloat重み**で行い、その後量子化する。

| アイデア | 初期化方法 |
|---|---|
| A1 | 特徴空間が別物なので蒸留（既存ネットでラベリング）か、スクラッチ |
| A2 | `ft-transplant`相当で既存HalfKPを移植し、スカラー列の重みを0 → 関数保存 |
| A3 | `stacks` で既存ヘッドを全バケットに複製 |
| A4 | 本体を移植、補助ヘッドのみ乱数初期化 |
| B1 | 既存HalfKPを移植し脅威FTの重みを0 → fine-tuneの差分が脅威特徴の寄与になる |
| B2 | P因子を既存HalfKPのP因子から初期化可能。それ以外はスクラッチ |
| C1 | `widen` / `deepen`（恒等層挿入）で関数保存的に構造変更 |

注意: 0初期化だけだと勾配対称性で新ユニットが死ぬことがあるため、**微小ノイズを入れる**。ワームスタート後は学習率を一度上げ直すか、新規部分だけ高LRにする。

### 1.5 学習データ・損失

- 入玉関連の特徴・バケットは教師データ中の入玉局面が少ないと重みが育たない → **入玉局面をオーバーサンプリング**（既存の `king_tracker.py` / `nyugyoku_extract.py` の抽出資産を使う）
- 蒸留データで学習する場合も勝敗項を完全に落とすと終盤精度が落ちやすい。lambdaは 1.0→0.75 のようなスケジュールを検討

## 3. 学習器（tatara）に関する確定事実と落とし穴

> 対象学習器は tatara で確定（2026-11-05）。以下は 2026-07 時点の調査結果のため、着手時に現行ソースで再確認すること。

- YaneuraOu-NNUE-features の全15アーキは `256x2-32-32` CReLU で共通。tatara の Simple サブコマンド（`--arch 256x2-32-32`, crelu）と同型。**入力特徴だけの変更ならGPUカーネル変更は不要**。
- tatara には既に LayerStack サブコマンド、threat 拡張（`--threat-profile`）、screlu / pairwise 活性化、psqt、FT factorizer（fold＋reduce方式、layerstack限定）がある。A3・B1・C1 はこれらの既存実装を起点にできる可能性が高い（**中身は要確認**）。
- `FeatureSet<A,B>` の index空間は**宣言の逆順**（後ろのBが低位）。
- 上流の `kHashValue` は複数特徴で衝突している（HalfKP/E4/E9/Kfile がすべて `0x5D69D5B8`）→ 自前で採番すること。
- エンジンは出力を `FV_SCALE=16` で割る固定実装。エンジンexportするランは **`--scale 508`** で学習する必要がある。
- `King24AttackEffect/DefenseEffect` は盤外マスをスキップするため手番側/相手側で活性数が非対称になる → nnz内の `-1` パディング契約が必要。
- 利き数の定義（遮蔽考慮・影の利きを数えない）がエンジンとズレると、学習は収束するのに実戦で弱くなる。**利き系特徴（B1・B2）でも同じリスク**があるため、エンジン側に一時的なindex dumpを生やして突合すること。
- 既存挙動（既存feature set / LayerStack / Simple / threat / factorizer）は bit-identical に維持し、既存回帰テストは無変更でpassさせる。

## 4. アイデア詳細

### A1. RelKP（玉相対座標KP）

**狙い**: HalfKPは玉が1マス動くと全パラメータが別物になる。玉からの相対座標で共有し、テーブル縮小と汎化を得る。教師データが少ない環境で収束が速い。

**特徴定義**
- 相対座標 `dx, dy ∈ [-8, +8]` の 17×17 = 289 オフセット × 盤上駒種（玉除く）
- 持ち駒は HalfKP と同じ絶対index（`fe_hand_end` までを流用）
- 次元 ≒ 8,182（HalfKP 125,388 の約1/15）

```cpp
inline IndexType MakeIndex(Square ksq, BonaPiece p) {
  if (p < fe_hand_end) return IndexType(p);          // 持ち駒は絶対
  auto [piece_kind, sq] = DecomposeBonaPiece(p);
  int dx = file_of(sq) - file_of(ksq) + 8;           // 0..16
  int dy = rank_of(sq) - rank_of(ksq) + 8;           // 0..16
  return fe_hand_end + piece_kind * 289 + (dy * 17 + dx);
}
```

**ネットワーク**: `RelKP[8182] → 256x2 → 32 → 32 → 1`。次元が小さいのでFTを512に広げる余地あり。
**差分更新**: 玉移動でrefresh（HalfKPと同じ）。推論側の変更は実質 `MakeIndex` のみ。
**factorizer**: 「駒種のみ」「相対座標のみ」の仮想特徴を推奨。
**リスク**: 盤端・敵陣/自陣の絶対情報が落ちる → 変種として「駒種×絶対段(9)」の補助特徴（+約2,500次元）を実特徴として足す案。端玉（穴熊）の表現力は要検証。

### A2. HalfKP＋入玉スカラー特徴

**狙い**: 入玉将棋で支配的な「点数勘定」「宣言条件までの距離」を、少数の密スカラー特徴としてL1に直接結合する。

**宣言ルール（確定：2026-11-05）**

初版は **CSARule27（27点法）**。後日 **CSARule24（24点法）** に切り替えられるよう、ルールは列挙型＋定数テーブルで持ち、特徴計算・エンジン・学習器の3か所が同じテーブルを参照する。

| 項目 | CSARule27（初版） | CSARule24（将来） |
|---|---|---|
| 点数（玉を除く、敵陣内の駒＋持ち駒） | 大駒5点・小駒1点 | 同左 |
| 勝ちに必要な点数 | 先手 **28点以上**、後手 **27点以上** | 31点以上で勝ち（24〜30点は引き分け） |
| 敵陣内の玉以外の駒 | 10枚以上 | 同左 |
| その他 | 玉が敵陣三段目以内、王手されていない、持ち時間が残っている | 同左 |

> 実装者へ: 上表は議論時点の理解。**やねうら王の `EnteringKingRule`（`EKR_27_POINT` / `EKR_24_POINT` 等）の実装を正**とし、閾値・判定条件をそこから写すこと。ズレがあれば報告する。

- 先後で閾値が違う（27点法）ため、特徴には「その玉の持ち主が先手か」を1ビットで渡す（視点反転しても閾値の非対称が分かるように）
- 24点法の「引き分け帯」は初版では特徴化しない。切替時に「31点までの残り」に加え「24点までの残り」を足す拡張余地として、ブロックの末尾に予約領域を置く

**スカラー特徴（確定：thermometer＋潜在宣言点数）**

各玉（手番側の玉・相手側の玉）について下表のブロックを計算し、`[手番側ブロック | 相手側ブロック]` の順に並べた**1本のベクトル**とする（手番で並び替え済みなので、us/them で2本持つ必要はない）。

| ブロック | 次元 | 定義（その玉の持ち主から見た量） |
|---|---|---|
| 玉の前進度 | 8 | 自陣最下段からの前進段数 d∈[0,8] を thermometer（`d≥1`, …, `d≥8`） |
| 玉が敵陣 | 1 | 玉が敵陣三段以内 |
| 敵陣内の駒数 | 10 | 敵陣内の玉以外の自駒数 n を thermometer（`n≥1`, …, `n≥10`） |
| 宣言点数の残り | 10 | r = max(0, 必要点 − 現在点)（現在点 = 敵陣内の駒＋持ち駒）を thermometer（`r≤0`, `r≤1`, `r≤2`, `r≤3`, `r≤5`, `r≤8`, `r≤12`, `r≤16`, `r≤20`, `r≤28`） |
| 潜在宣言点数の残り | 10 | 盤上全自駒（玉除く）＋持ち駒で数えた点数に対する残り。区切りは上と同じ |
| 持ち駒点数 | 1 | 持ち駒の点数 / 必要点（0〜1にclamp） |
| 宣言条件の成立 | 1 | 王手・持ち時間以外の宣言条件をすべて満たす |
| 先手フラグ | 1 | その玉の持ち主が先手 |
| 予約（24点法用） | 2 | 初版は常に0 |
| **計** | **44** | |

- 2玉分で 88次元 → **96次元にパディング**（32の倍数）
- 区切り値は定数テーブルに置き、学習比較で調整できるようにする
- 入玉可能経路数（敵利き依存）は利き計算が必要なので初版では入れない（B1で利き計算基盤ができてから再検討）
- 毎回O(駒数)で再計算（差分更新しない）。コストはFT差分更新に比べ無視できる

**フォールバック**: 実装・ビルドで問題が出た場合は、旧仕様の **one-hot＋正規化スカラー**（玉の段 one-hot 9、敵陣内駒数/10、宣言点数/28、残り点数、持ち駒点数）に切り替える。符号化は `ScalarEncoding { Thermometer, OneHot }` のフラグで持ち、両方を同じ96次元枠に収める（one-hot版は未使用部分を0）。ネットのハッシュには符号化種別とルール種別を含め、取り違えをロード時に弾く。

**ネットワーク**
```
HalfKP[125388] --FT--> 256x2              … 従来どおり差分更新
NyugyokuScalar[96]（手番順、int8）  ──┐
                                      ├ concat → 608 → 32 → 32 → 1
```
- スカラーは 0/1 または 0〜1 の値。`round(x*127)` で int8 化し、CReLU後のFT出力と同スケールに揃える
- シリアライズは L1 の列数が増えるだけ。書き出し順は「FT列（手番側256→相手側256）→ スカラー列96」
- ローダは sparse 特徴とは別テンソルでスカラーを返す

**参考**: thermometer化と潜在宣言点数は、DL将棋の `NYUGYOKU_FEATURES2` 検討（one-hotは閾値を超えると勾配が切れる、敵陣内の駒しか数えないと潜在的な点数が見えない）から持ち込んだもの。

#### A2 の実装方針（tatara＋やねうら王を同時改造）

> tatara のクレート名・ファイル名は 2026-07 時点の調査に基づくため、**着手時にリポジトリを読んで実在を確認**し、異なれば実ソースに合わせること。やねうら王側も同様に、現行ソースの NNUE ディレクトリ構成を確認してから着手する。

**位置づけ**: A2 は sparse 特徴（FT）の変更ではなく、**FT出力の後ろに密な入力を連結する**変更。tatara の既存の feature set／sparse カーネル／factorizer には手を入れない。変更は tatara の dataloader・Simple 系 trainer・export と、やねうら王の評価関数（forward と L1 入力次元・ロード処理）に集中する。

**作業環境（§7 も参照）**: tatara とやねうら王の2リポジトリを1つのセッションに置いて作業する。GPU が必要な工程（学習 smoke、GPU/CPU 同等性テスト）は GPU のある手元マシンで実行し、それ以外（スカラー計算、export、エンジンのビルドと integer-exact 突合）はクラウドでも進められる。

**段階分け（各段階を独立PRにする。T＝tatara、Y＝やねうら王）**

1. **調査とADR**（T・Y）
   - T: Simple trainer の forward/backward で FT出力が L1 にどう渡るか（連結済みバッファか、カーネル内で直接読むか）を特定する。ここで「L1入力に列を足す」改造の難易度が決まる
   - T: `--arch` の任意次元対応の実装を確認し、L1入力次元を「2×FT幅＋96」として扱えるか判断
   - T: GPU を使わずに forward を計算できる CPU 参照実装があるか確認（integer-exact 突合と、クラウドでのテストに使う）
   - Y: `evaluate_nnue.cpp` の forward、L1（AffineTransform）の入力次元とパディング、`EnteringKingRule` の判定実装を確認
   - 結論を ADR に記録（スカラーを Simple の拡張オプションにするか別サブコマンドにするか、ルール・符号化の定数テーブルを両リポでどう共有するか）
2. **スカラー計算モジュール**（T・Y、CPU完結）
   - 本節の表（thermometer＋潜在宣言点数、CSARule27）どおりに、T（Rust）と Y（C++、`features/scalar_nyugyoku.h` 相当）の両方に実装する
   - ルール（`Csa27` / `Csa24`）と符号化（`Thermometer` / `OneHot`）は列挙型＋定数テーブル。初版の既定は `Csa27`＋`Thermometer`
   - 2言語で同じ値を返すことを保証するため、**golden 局面ファイル（SFEN と期待スカラー列）を1つ作り、両リポのテストが同じファイルを読む**
   - golden 局面: 初期局面、中盤、片側入玉、相入玉、宣言条件をちょうど満たす局面（先手28点・後手27点の境界）、境界の1点手前
   - property テスト: 盤面を180°回転し先後を入れ替えると、ブロックの並びが入れ替わる（先手フラグを除く）
3. **dataloader 配線**（T）
   - `Batch` に密スカラーのテンソル（batch × 96）を追加。sparse の nnz 契約は変えない
   - スカラー無しの既存プリセットでは確保しない（既存挙動を bit-identical に維持）
4. **trainer 拡張**（T、GPU）
   - L1 の入力を `[FT_stm(256) | FT_nstm(256) | scalar(96)]` とし、重み行列の列を追加
   - 初期化: スカラー列の L1 重みは 0＋微小ノイズ。既存 HalfKP ネットからのワームスタート時に関数保存になることをテストで確認
   - smoke: 数 superbatch で loss が減ること、スカラー列の重みのノルムが 0 から動くこと
5. **export と推論**（T・Y）
   - T: スカラー列は int8（`round(x*127)`）。L1重みの列順は「FT列 → スカラー列」、パディングは32の倍数。`--scale 508` 前提（§3）
   - T・Y: 新ハッシュ値（符号化種別・ルール種別を含める）を採番し、byte-golden テストで出力バイト列を固定
   - Y: forward 直前にスカラー96次元を構築して L1 入力末尾に連結。L1 入力次元を 512→608 に拡張。ビルドフラグ（例: `NNUE_ARCHITECTURE_HALFKP_NYUGYOKU`）で既存アーキと切り替え
6. **検証**
   - §1.2 の4段階。まずランダム1万局面で T と Y のスカラー値（int8化後）を突合し、その後 integer-exact（T の量子化 forward と Y の `Evaluate()` が±0で一致）
   - 棋力: 通常局面のレート変化と入玉局面集での宣言勝ち到達率（§1.3）。対局は手元環境で行う

**教師データ**: 入玉局面のオーバーサンプリングを前提とする。比率は学習比較で決める（§6）。

**完了条件（DoD）**
- 両リポの既存回帰テストが無変更で pass
- 共有 golden ファイルを使ったスカラー計算テストが T・Y の両方で green
- ワームスタート直後の出力が元ネットと一致（float誤差内）
- export した `.bin` を Y が読み込み、integer-exact 突合が全局面で一致

### A3. 出力側バケット（LayerStacks）

**狙い**: FTは共有し、L1以降をバケット別に持つ。序中盤・終盤・入玉戦で評価の「文法」が違う問題を出力側の分岐で解く。FT差分更新には影響しない。

**バケット関数の候補**

- 旧仕様書案（8バケット）:
  ```
  bucket = min(7, 盤上駒数 / 6)
  if (どちらかの玉が敵陣) bucket = 7   // 入玉専用
  ```
- バケット分割議論（7/27）での改良案（16バケット）:
  - 軸1: **持ち駒総数**（4分割、進行度の代理）
  - 軸2: **入玉度**（通常／自玉入玉模様／相手玉入玉模様／相入玉の4分割）
  - 4×4=16。数百億局面規模の教師で占有率の下限付近

**良いバケット軸の条件**: FT特徴と直交している／対局中に緩やかに遷移する／実戦分布で占有率が偏らない／評価の体制が本当に変わる／O(1)で計算できる。
- 玉位置バケット（k3k3〜k81k81）はHalfKP/HalfKAのFTが既に玉位置で条件付けているため効果が重複しやすい。細かすぎると兄弟局面間で評価が不連続になり、aspiration windowや枝刈りマージンに悪影響。
- 制約は計算量ではなく**バケットあたりの教師データの断片化**。細分化で検証lossが良く見えても、少数バケットの過学習が隠れていることがある。

**構造的な代替案（バケット数を増やす前に検討）**: 共有ヘッド＋バケット残差、連続軸でのソフト割り当て（補間）、希少バケット崩壊を防ぐ補助損失、残差誤差のクラスタリングによるデータ駆動の分割設計。

**リスク**: 入玉バケットのサンプル不足 → オーバーサンプリング、または全バケットを同一初期値から開始（`stacks`）。

### A4. 宣言勝ち補助ヘッド（学習側のみ）

**狙い**: 推論バイナリを変えずに、FTの表現に入玉認識を染み込ませる。

```
FT出力512 ─→ 本線 32-32-1 (eval)      loss = 通常のeval/勝敗混合
        └→ 補助 32-1 (sigmoid)        loss = BCE(宣言勝ち到達フラグ), 重み α≒0.2
```
- ラベル: 「その対局が宣言勝ち/入玉勝ちで終わったか」を `game_result` 拡張または並行ラベルファイルで持つ（cshogiベースの対局フレームワークの入玉判定を流用）
- 書き出し時は補助ヘッドを捨てる。エンジン・index生成は無変更
- 単独効果は限定的だが、他のどの案とも併用可能。学習パイプライン改造の練習台として最適

### B1. 将棋版 FullThreats（HalfKP＋利き関係特徴）

**背景**: Stockfish 18（SFNNv10）で導入。「駒Aが駒Bに利いている」駒ペア関係を1特徴とし、HalfKAv2_hm と併用する（脅威のない局面を区別できないため単独では使わない）。KPPT時代の2駒関係の一部を「利き」で絞って取り戻す構図で、将棋と相性が良いと見ている。SF側では脅威特徴の導入でL1を縮め、浮いた計算をL2の倍増に回した。

**特徴設計**
- 単位: (視点, 攻撃駒, from, to, 被攻撃駒)。味方駒への利き（ひも）も含む
- **攻撃側の駒種圧縮**: 金・と・成香・成桂・成銀は利きが同一 → 1種に。被攻撃側をまとめるかは実験で決める
- 次元: 素朴に数十万 → 圧縮後 **10万〜20万程度**の見込み
- **玉非依存**で開始（視点の180°回転のみ）。左右ミラーのバケットは第2段階
- **冗長ペア除去**: 「(A@s→B@t) が成立すると (B@t→A@s) が必ず成立」する組を**機械的に全列挙**して削る（将棋は向きが非対称なのでルール手書きは危険）。例: 先手歩→後手金は冗長
- 持ち駒は盤上に利きがないので対象外（従来の持ち駒特徴に任せる）

**学習側**
- PSQ（HalfKP）のFTと**同じ幅の別FT**を持たせ、活性化の前に加算
- 重みはint8、アキュムレータはint16
- 初期化は既存HalfKP移植＋脅威重み0（§1.4）
- factorizer: 「駒種ペアのみ」「相対位置のみ」の仮想特徴で立ち上がりを速くする

**エンジン側**: まず全リフレッシュ版でElo上限を測り、その後に差分更新（dirty threats）を実装。将棋の難所は、飛び駒が5種（香・角・飛・馬・竜）、打ち駒が「追加のみで遮りを生む」、駒数40枚で脅威数がチェスより多い、の3点。

**計測順**
1. 教師局面で脅威特徴数の分布（平均・最大）と1手あたり差分数を集計
2. 固定ノードでElo上限
3. 固定時間でNPS込みの実効値

**撤退基準の目安**: 固定ノードで+30 Elo程度でもNPSが15%以上落ちると相殺されうる。効果が薄ければ、駒種圧縮や玉ミラーより先に**対象駒種を大駒・金銀に限定した縮小版**を試す。

**関連**: 3層化案 `(HalfKA_v2+FullThreats)_1024x2-32-1` は C1 で扱う。

### B2. Threat-NNUE（玉非依存：P＋T＋Z）

**狙い**: HalfKP/HalfKAの本質は「疎で1手ごとの差分が小さい文脈索引」であり、玉位置の代わりに**利き関係を文脈にする**ことで、K索引なしで相互作用を取りつつ玉移動時のリフレッシュをなくす。

**入力特徴（多重度つき加算でアキュムレータに載せる）**

| ブロック | 定義 | 次元 | 活性数・差分 |
|---|---|---|---|
| P | (駒種, マス)＋持ち駒(種類×枚数) | 約2.5k | 毎手2〜4個更新 |
| T | (攻撃側駒種×手番 28, 被攻撃駒種 28, 被攻撃マス 81) | 約63.5k | 常時60〜90個、10〜20個/手 |
| Z（任意） | (玉からの相対5×5, 自利き数{0,1,2+}, 敵利き数{0,1,2+}) | 225 | 玉移動時に25マス再計算 |

- Tの要点: **対象を「駒のあるマス」に限定**する。飛角香の利き先は各方向の最初の遮蔽駒だけなので1駒あたり最大4個。玉は攻撃者・被攻撃者の1駒種として現れるだけで索引に使わない
- 「Kを完全排除」したいならZの代わりに、Tの被攻撃駒種に「自玉隣接フラグ」1ビットを足す方が安い
- 空マスへの利き（拠点・厚み）はスライダー移動で20〜30マス変わるため全盤では持たない

**バケット**
- 入力側: 玉位置の代わりに**局面フェーズ**（駒台の枚数＋盤上非歩枚数の粗いビン、4〜8個）でP/Tの重み表を切替。切替は駒取り時のみなので、**finny table**（バケットごとのアキュムレータ＋盤面キャッシュ）で差分復元し、全再計算をゼロにする
- 出力側: フェーズ＋入玉度（玉の段≥4）で8スタック（A3と共通）

**後段**: アキュムレータ 2×512〜1024 → CReLU → 隣接要素のペア積（幅半分・L1入力を疎化）→ int8疎L1(16) → L2(32) → 出力

**コスト見積り**: アキュムレータ加減算は1手あたり片視点20〜30回（HalfKP256は2〜4回＋玉移動時の全再計算≈40回）。遅延評価込みで探索全体では **HalfKP256の1.3〜1.8倍**程度の見込み。

**学習**: Tは「攻撃駒種×被攻撃駒種」と「被攻撃駒種×マス」の周辺表を因子分解器として足す。後者はPと共有でき、既存HalfKPのP因子から初期化可能。技巧の利き項（線形）の重みと学習後Tの周辺表を比べると特徴設計の当たり外れが早く分かる。

**アブレーション順**: P単独 → +T → +Z（または隣接フラグ）→ フェーズバケット

### C1. 後段構造の比較

**論点**: 後段のコストは「FT直後の層の出力幅」でほぼ決まる。最終隠れ層を削っても速くならない（`1024x2-8-32-1` ≈ 1.7万積和、`1024x2-32-1` ≈ 6.6万積和）。チェスの上位エンジンは浅層から多層に移行しており、逆の例は見つかっていない。単層の出力はFTニューロンの線形和なので「玉が薄い」かつ「相手が角を持つ」のような相互作用を作れず、持ち駒・打ち駒のある将棋ではこの欠落が効きやすい。一方でFullThreats（B1）は相互作用を入力側で肩代わりするため、併用時は損失が小さくなる可能性がある。

**比較セット（同程度のNPSで）**
- A: `1024x2-32-1`
- B: `1024x2-16-32-1`
- C: `1024x2-32-32-1`
- D: `1024x2 → 1×8`（出力バケット付き単層、極端な基準）

**浅くするなら併用する工夫**: SCReLU（二乗CReLU）またはペア積、駒数・進行度による出力バケット。
**浅層の有力な用途**: 教師局面生成用の低深度探索、超短時間対局向けの小型ネット。

### C2. FTの低bit量子化

**結論（議論時点）**: 従来のCPU推論では16bit小規模モデルの方が勝つ可能性が高い。2bit大規模モデルが勝つにはQATとメモリ帯域ボトルネックが条件。
- アキュムレータはint16以上が必要で、L1を広げると差分更新・再計算・スタック保持のコストはL1幅に比例
- AVX2/AVX-512に2bit演算命令がなく、展開コストが削減効果を食う
- fp32学習後の事後2bit量子化は精度が壊滅的

**実験案**: FTの重みだけ2bit/ternaryにして**QATで学習**、後段は従来のint8。比較は「メモリ量を揃える」「固定ノード」「固定時間」の3条件。固定ノードで勝ち固定時間で負けるなら、ボトルネックは実装（展開コスト）側。
